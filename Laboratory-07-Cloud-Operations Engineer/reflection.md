During this lab, I learned how crucial host system health is when running containerized applications. Even when containers perform well, they share the host’s underlying CPU, memory, and disk space. If the host runs out of resources, every container suffers. In my baseline test, the server had 1.9 GiB of RAM and 19 GB of disk storage. Monitoring these physical limits ensures the server will not crash during sudden traffic surges. I also learned the difference between logs and metrics. Logs capture individual events, showing exact timestamps and status codes. For example, when troubleshooting a failed user login, looking for 401 or 403 errors explains access issues, while a 404 error points to missing pages. In contrast, metrics measure resource usage over time. Seeing 2.699MiB memory usage and 0.00% CPU in docker stats showed my idle container was lightweight, but active traffic will change these numbers. If a web page is slow, I check metrics first; if it returns errors, I inspect the logs. For large-scale operations, tools like Prometheus collect metrics automatically across thousands of containers, while Grafana displays them on visual dashboards with real-time alerts. Manual monitoring commands do not scale well in enterprise environments. Finally, my troubleshooting skills improved through practical mistakes. When I typed curl twice by accident, I received a "Could not resolve host" error. Checking docker logs helped me see that seven successful requests occurred instead of three. Tools like docker stats were new to me, and I now feel more confident using terminal logs to fix real application errors.
